# Cairnpath engagement engine

A hands-on demo project: a signal-triggered customer engagement engine.
Fake product usage data goes in; flags come out that tell Customer Success
when to act and what to do. Built locally first, then moved to AWS.

The owner (Nikodem) is a Customer Success leader rebuilding hands-on
technical skills. Explain changes in plain language, keep code readable
with short comments, and work in small steps (one PR per change).

## Working rules

- How we work (a low-stakes demo; keep Nikodem's effort minimal): Claude
  writes the code, pushes a `claude/...` branch, opens a PR, checks it as
  far as it can, then merges it itself. Never push to main directly, never
  commit secrets. Nikodem doesn't review code; he runs `.\run_all.ps1`
  when asked (pull + the whole pipeline), and Claude reads the output from
  `data/last_run.txt` on his laptop. Ask him only for things only he can do:
  Slack clicks, app settings, decisions about CS logic.
- Windows + PowerShell. Activate the env with `.venv\Scripts\Activate.ps1`,
  run scripts from the repo root (paths are relative to it).
- Pinned dependencies live in `requirements.txt`. Add, never overwrite.
- Thresholds and time windows live in `settings.toml`, not in the scripts.
- Integrations are configuration, not code: anything tied to one workspace,
  account or environment (Slack channels and member IDs, URLs, the LLM model
  and price, later AWS region and bucket) lives in its own `settings.toml`
  section ([slack], [slack.users], [llm], ...); secrets live only in `.env`.
  Moving to a new Slack workspace or provider = edit settings and .env, never
  a script. Apply this to every new integration.
- `data/` is generated by `generate_events.py` and is git-ignored.
- Keep it lean: no new flags, tables or tools without a reason.
- Testing, in tiers (Claude runs them in its own sandbox; Nikodem never
  has to): every PR that touches the engine runs the engine checks
  (check_inputs, check_flags, backtest); every PR that touches the cockpit
  also runs the cockpit test (`node tests/cockpit_test.js`, about a minute)
  and the site test (`python roles.py --site`, then `node tests/site_test.js`).
  The scenario tests (`node tests/scenarios_test.js`, about two minutes) run
  before a demo or milestone, after a regenerate, or when a change touches
  roles, routing, money or the segment bar; their results go to the
  acceptance page. Every PR that touches infra/ runs `python
  tests/infra_test.py` (builds the template in memory, no AWS login, no
  cost), `python tests/check_lambda_test.py`, `python
  tests/engine_lambda_test.py` and `python tests/slack_lambda_test.py` (the Lambdas' handlers against a stand-in S3); so does
  any PR that changes what an engine step imports (engine_lambda_test checks the
  bundle has it: #120 added roles.py to export_views.py and only #127 bundled it); one that touches upload.py runs `python tests/upload_test.py`; one that touches slack_loop.py or listener.py runs `python tests/slack_lambda_test.py`; one that touches pull_clicks.py runs `python tests/pull_clicks_test.py`; one that touches llm.py, brief.py or handover.py runs `python tests/ai_spend_test.py`; one that touches cockpit_sync.py runs `python tests/cockpit_sync_test.py`; one
  that touches roles or policies also runs `python tests/security_check_test.py`
  and, after the deploy, Nikodem runs `python security_check.py` (live). Docs-only PRs need none. Nothing merges with a FAIL. A bug
  found by hand gets a test that would have caught it.
- Fix review findings now, in the same change or PR. Don't defer them to
  "later": deferred fixes get lost.
- When a fix or concept has a real-world angle (something a TAM meets
  with customers, or a good interview story), add a short tip on it.
  Keep it brief and only when it's genuinely useful.

## Scope: a CSM cockpit

This is a cockpit for the CS team, not an org-wide engagement tool.
- Customer messaging triggered by usage or plan limits belongs to Product.
  Churn and expansion flags never send usage, plan-limit or upgrade
  messages: they ask the pool or CSM to investigate and analyse (the one
  email is Self-service Shelfware's adoption content, below).
- Self-service churn and expansion rows go to the Self-service report
  (routed_to = 'report') for analysis across accounts.
- Onboarding programmes (activation welcome emails, workshop invites) stay:
  they are CS one-to-many engagement, not utilisation messaging. So does
  adoption content for Self-service (e.g. the use-case inspiration email for
  Shelfware): it teaches, it never mentions plan limits or upgrades.
- Apply the same test to anything new: investigate and analyse first.

## The fake product

Cairnpath, a fictional product analytics SaaS. Customers pay for an
annual committed event volume; seats are free and unlimited; paid add-ons
(e.g. experiments) are the expansion path.

## Tiers

| Tier | CS coverage | Where flags go |
| --- | --- | --- |
| Self-service | None | Automated emails and self-onboarding |
| Scale | Pooled CS team | Shared CS queue, workshop invites |
| Enterprise | Named CSM | Straight to the CSM, plus QBR briefs |

Book of business: ~500 accounts, Europe only, in four sub-regions
(UK&I, DACH, France & Benelux, Nordics). 48 Enterprise (6 CSMs, 8 each),
150 Scale (one pooled team per region: a queue plus named members, about 1
per 15-20 accounts: UK&I 3, DACH 2, F&B 2, Nordics 1), 300 Self-service. Show counts next
to percentages in reports: small segments mislead.

CRM table (`data/crm_accounts.csv`): account_id, account_name, tier, region,
contract_start, renewal_date, contracted_events, add_ons, csm_owner
(Enterprise), cs_pool (Scale: the queue tasks go to), pool_owner (Scale:
the named pool member who owns it, optional), last_qbr_date and next_qbr_date
(Enterprise, roughly quarterly; some overdue and not rebooked), arr (optional;
missing = estimated from contracted_events x the list price in [money]).
Contract sizes vary per account (half to double the tier's middle size).
Pipeline-written facts
(e.g. "welcome sent") go in an action log, not the CRM.

CS team table (`data/cs_team.csv`): owner_id, owner_name, owner_type
(csm | pool | member), region, manager, pool (a member's pool). Scale
accounts get a named member in turn (round robin per pool, no random draws);
meetings on them are that member's, workshops stay the pool's. Tasks still go
to the pool queue; the cockpit counts a member's work as tasks routed to them
plus pool-queue tasks on their own accounts.

## Event schema

One JSON event per line, one file per day in `data/events/`.

- All events: event_id, event_name, event_type (product | system),
  timestamp (UTC), account_id
- Product events only: user_id
- Optional: properties, context
- Product events: sdk_installed, chart_created, dashboard_shared,
  cohort_created, experiment_launched, user_invited, data_export
- System events: daily_event_volume (properties.event_count),
  ingestion_error (properties.error_code)
- Derived in SQL, never emitted: first event / go-live date
- Engagement events (`data/engagement/`, view `engagement`, event_type
  engagement): email_sent, email_opened, workshop_attended, meeting_held,
  with properties.owner_id (csm_*, pool_*, automated) and properties.topic
  (getting_started, onboarding_workshop, advanced_workshop, qbr, kickoff,
  check_in, churn_call, activation_call, growth_call, follow_up; from actions.py: welcome_pack,
  invite_your_team, need_help_starting, use_case_inspiration; follow-ups
  invite_your_team_followup, need_help_starting_followup, customer_story). user_id = the customer user who
  responded or attended. context.source says who wrote it (cs_history from
  the generator, actions.py for new actions, slack for clicks, cockpit for
  managers' decisions). Slack clicks add task_claimed events and meeting_held
  with properties.outcome, .note and .slack_user. The cockpit adds
  task_assigned (properties.owner_id = new owner, topic = flag, .status,
  .manager), handback_approved and forecast_set (a renewal forecast: .status =
  renew | downsize | churn, .amount, .note = reason, .owner_id = who,
  .outcome = owner | manager; internal, never a customer touch) and
  next_step_set (action planned: .status = call | qbr | email | internal,
  .due, .note, .owner_id, .outcome; internal too).

## The four flags

1. Activation (contracts from the last 45 days only). Statuses:
   - Activated: SDK installed and 2+ active users within 14 days of
     contract start
   - Activating: under 14 days, not all signals yet (no action)
   - Stalled: 14+ days, SDK in but fewer than 2 users
   - Silent: 10+ days since contract, no events at all
   - Handoff gap: events but no CRM row (alert CS ops, no customer email)
   - No CSM assigned: Enterprise account in scope with empty csm_owner
     (alert CS ops)
   Actions route by tier: Self-service automated, Scale to the regional
   pool, Enterprise to the named CSM.
2. Churn risk (accounts live for the full 90 days). Usage signals:
   utilisation under 40% and lower each month for two months; weekly
   active users 30%+ below their 90-day average and at least one whole user
   fewer (small accounts). One = Watch, both = Act.
   Ingestion errors (5+ in 30 days, rising) only count next to a usage
   signal, and push Watch up to Act with a "technical check first" action.
   Self-service rows go to the Self-service report.
   Shelfware: live 60+ days (go-live) and 30-day utilisation never reached
   40%: flat and low, never ramped up. Status Shelfware. Scale and
   Enterprise: adoption review and a ramp plan before renewal (renewal
   within 3 months: call this week about the renewal volume). Self-service:
   automated use-case inspiration email (topic use_case_inspiration).
   Accounts already at Watch or Act keep that status.
3. Expansion (accounts live for the full 90 days). Stays with CS: the
   CSM builds the growth case, Sales only signs. Volume signal: 90%+ of
   contract already, or 80%+ and climbing 3+ points a month fast enough to
   pass 90% before renewal. Breadth signal: active users up 25%+ in two
   months. Volume + breadth = Act (action depends on timing: overage now,
   renewal within 3 months, or mid-term). Volume only = Watch with a
   tracking check (rising volume with flat users is often over-tracking).
4. QBR (Enterprise). QBR coming up: next QBR in the next 30 days, so the
   CSM prepares it; `qbr.py` builds a facts pack per account (usage,
   forecast, weekly active users trend, underused add-ons, pseudonymised
   key users, champion trend, errors, open flags). A champion is a top user
   doing 2x+ what the next one does; otherwise "no single champion". QBR overdue: live 4+ months, last
   QBR 120+ days ago or never, nothing booked in 30 days: book one.
   `brief.py` has an LLM (Claude Sonnet 5.5 via the Anthropic API) write a
   one-page brief per pack, ending with one suggested ask. Every number in
   the draft is checked against the pack; untraceable ones are listed as
   "unverified" at the bottom. Real user IDs go back in after the model.
   QBR first: with a QBR in the next 30 days, an Enterprise account's churn
   and expansion flags get no separate task. The QBR task lists them ("also
   in the brief"), they're logged "covered by the QBR", no "No meeting"
   escalation, and team_report.py counts the QBR as the action when the
   signal came in the 30 days before it. The flag rows stay, for tracking.
   If the QBR date passes with no QBR held (view qbr_slips, from the action
   log), the flag is raised again as a normal task, never handed to a QBR
   again, and a newly booked QBR no longer holds back the escalation.

## Design rules

- SQL computes every fact; the LLM only writes them up.
- Every flag shows its reasons (e.g. "utilisation 32% and falling").
- Actions are sent once only (idempotent), logged in the action log.
- Users are pseudonymised before anything reaches an LLM.
- Use the data's as-of date (max event date), never today().
- Utilisation divides by days live in the window (max 30), so new
  accounts aren't penalised and silent days still count.

  [utilisation], so the SQL downstream always speaks the engine's names

  QBR that didn't happen, from the action log), action_status (every task

  Every script uses it; define views here, once.
- `explore.py`: DuckDB summaries by tier, region and CSM, plus CS
  engagement week by week and meetings by owner.
- `flags.py`: the activation, churn and expansion flags. One row per
  flagged account, with reasons, routed_to and action; saved to
  `data/flags_activation.csv`, `data/flags_churn.csv` and
  `data/flags_expansion.csv`; the QBR flag to `data/flags_qbr.csv`.
  Also the value at stake per churn and expansion row (view account_value,
  `data/account_value.csv`, with its basis): ARR at risk per status from
  [money.at_risk] in settings (a share of ARR, or "unused" = ARR x (100% -
  utilisation)); today the whole ARR at Act (they may leave), the unused part

- `check_flags.py`: tests the flags against the answer key (run `flags.py`
  first): share of each personality found, false alarms, and every miss by
  name. Re-run it after any change to a flag rule.
- `backtest.py`: did the churn flags see it coming? (run `flags.py` first)
  Against `data/renewal_outcomes.csv` (what happened at each renewal in the
  180 days after the data: renewed, expanded, downsized, churned; written by
  the generator with its own random generator, including surprise churn no
  flag can see, and better odds for declining accounts that got a churn
  call): recall, precision, warning time (first day under the churn line to
  renewal; under [backtest] too_late_days = too late), misses by name, and
  churn with vs. without a churn call (Act accounts only: mixing flag types
  confounds it), and the sieve read like a funnel (churn signals -> to
  automation or a person -> Act -> called -> called within 14 days ->
  renewing -> kept whole), and value: the data's ARR at risk and the owners'
  latest forecasts next to the ARR really lost (ARR - renewal_arr, an optional
  outcomes column; the generator shrinks a downsize to about the account's
  usage, so it shows the method, not proof). Runs after team_report.py (uses time_to_action).
  Not done yet: replaying the flags as of an earlier date (needs a longer
  data window).
- `journeys.py`: rules on the last touch (run `flags.py` first). "Email
  never opened": Self-service stalled/silent, getting-started email 5+ days
  old and unopened -> CS ops checks the contact. "No meeting in 30 days":
  churn or expansion Act (Scale/Enterprise) for 14+ days with no meeting
  in 30 days, and no QBR booked in the next 30 days ->
  escalated to the owner's manager (one Slack message per manager).
  "Follow-up not picked up": a Scale follow-up named to a person, still
  Open after 5 days -> their manager approves handing it back to the pool
  ("Approve hand-back" button; actions.py then sends it to the pool).
  "Reassigned, not picked up": a task a manager reassigned in the cockpit,
  still Open after 5 days -> back to that manager. Saved
  to `data/flags_journey.csv`, same columns as the flags.
- `team_report.py`: time to action by owner and manager (run `flags.py`
  and `journeys.py` first). Signal date = first day the account's 30-day
  utilisation crossed the flag's line (rebuilt from usage); call date =
  first churn, growth or activation call (check-ins don't count; a QBR
  counts when the signal came in the 30 days before it, column via);
  a call up to 14 days before the signal counts as 0 days ("called
  early"). Also escalations and meetings in 90 days. Action status (view
  action_status in cairnpath_db.py): each task Open, Claimed (Slack),
  Done (the right meeting since it was sent: churn -> churn call or QBR,
  expansion -> growth call or QBR, QBR -> the QBR, activation and
  escalations -> any meeting; a check-in never closes a churn task) or
  Resolved (the flag went away; the only way CS ops tasks close), with its
  age. Managers see unclaimed pool tasks and CS ops items, oldest first.
  Outcome not measured yet.
- `onboarding_report.py`: welcomed vs. control (run `generate_events.py`
  first). New Self-service/Scale accounts that got the getting-started email
  vs. the onboarding holdout: SDK installed, median days to SDK and to first
  chart (speed), activated in 14 days for accounts 14+ days old (outcome),
  overall and by tier, counts next to percentages. Planted effect: shows the
  method, doesn't prove emails work.
- `export_views.py`: everything the views need, to `data/views_data.json`
  (run `generate_events.py`, `flags.py` and `journeys.py` first). Reuses the
  reports' SQL through `team_report.add_views(con)` and
  `onboarding_report.add_views(con)`, so the page and the reports agree.
  Counts only, never real user IDs. Also builds `data/views.html` from
  `views_template.html` (the data goes into its `__VIEWS_DATA__` slot): nine
  tabs. Overview (the engagement sieve: churn signals stage by stage, and
  renewals in the next 180 days by today's flag), Leadership (the one-pager:
  ARR at risk with action taken, renewal, action planned and forecast, biggest
  first; growth by upside; Act accounts called and planned; forecasts ≠ data;
  meetings and share of the book met in 30 days per owner against the median
  of the same kind), My book (one owner's
  morning page: workload, engagement against the median of owners of the same
  kind, the portfolio risk first with action taken and planned, and booked
  engagements over the next 8 weeks: QBRs, renewals, Scale follow-ups), Tasks (the manager's queue:
  every task sent to a person, its status and age; in the published cockpit a
  manager gives one to someone else or approves a hand-back, saved in the
  page's database), Did it work? (the backtest:
  caught / missed / false alarm, warning time, calls, ARR at risk vs. really
  lost by status), account timeline,
  onboarding, CS team (with capacity: each owner's whole book and open
  tasks against the median, for cross-region pickup), book of business (with
  accounts covered from another region). Every bar, cell and stage lists its
  accounts on click, and a row opens that account's timeline, so the logic can
  be checked by hand. A segment bar filters by people (manager, team = the region the owner
  sits in, owner) and by accounts (region = where the customer is, tier); it filters
  every tab; on the timeline it picks the example chips (and opens an account
  in the segment when the segment changes; one opened from outside is marked
  "Outside <segment>"). The lists narrow each other: each offers only
  values that still have accounts under the other filters. Its Find box (and the timeline's) searches
  accounts by name or ID, the segment's first. The Owner list has named people only: a pool is
  Team + the Scale tier. Values: ARR per account, ARR at risk and upside per
  flag (My book sorts by them). Renewal forecast on the timeline: the data's
  number, then the owner's or their manager's call (renew, downsize to an
  amount, churn) with a reason, saved in the page's database with its history;
  a quarter of the ARR apart from the data = flagged "≠ data". Action planned
  on the timeline too: the owner's (or manager's) next step with a date, else a
  QBR booked in the CRM; overdue when the date passes with no meeting since it
  was set; shown in My book's portfolio. The timeline opens with a summary:
  everything done (customer touches, tasks sent, plans, forecasts), newest
  first, next to what's coming up (next step, booked QBR, renewal with its
  forecast). Handover brief on the timeline (accounts with a finished brief
  from handover.py, exported as handovers): the brief as a draft, each
  citation a tag that opens that source as the model saw it (redacted), what to
  check before confirming, and Confirm (optional note for the new owner) for
  the outgoing owner or their manager, saved in the page's database
  (handover_confirm, pointing at the brief's version = its written_at); a
  rewrite after that makes it a draft again. Also exports next_steps,
  forecasts (forecast_set events), churn_signals, renewals
  (backtest.py's view) and tasks (action_status, with each task's manager).
  Opens in any browser offline. The page only draws; the numbers come from
  the export.
- `roles.py`: one cockpit page per person (ROLES.md, settings.toml [roles]),
  called by export_views.py, or `python roles.py` on data/views_data.json. Cuts
  the export to the person's accounts (the team = everyone under one manager;
  Self-service for managers in their team's regions; the leader the whole book),
  takes the role's missing tabs out of the HTML, swaps "Did it work?" for team
  totals below manager level (no row per account), and writes a page-meta block
  (person, role, tabs, accounts, edit rights per action). The page reads it to
  open on the role's first tab and to offer a form only where the person may act.
  Writes data/pages/<owner_id>.html, leader.html and index.html (the landing
  page, with a switcher to every page: demo only, see THREAT_MODEL.md).
  `python roles.py --site` (an engine step in AWS) writes the same pages in
  sandbox mode to data/site/ for the public demo site: forms save in the visitor's
  browser only (localStorage, "Clear my changes"), a banner says so, and the
  switcher simply opens the other page's address. `tests/site_test.js` serves them
  with the site's real content policy. Published,
  only the main page gets the database, so the switcher fetches the chosen file and
  writes it into the main page (stopping the old page's database listener first);
  offline, where fetch can't read files, it opens the file instead.
