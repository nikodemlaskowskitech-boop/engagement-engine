# Cairnpath engagement engine

A hands-on demo project: a signal-triggered customer engagement engine.
Fake product usage data goes in; flags come out that tell Customer Success
when to act and what to do. Built locally first, then moved to AWS.

The owner (Nikodem) is a Customer Success leader rebuilding hands-on
technical skills. Explain changes in plain language, keep code readable
with short comments, and work in small steps (one PR per change).

This page is the short version: rules, the business logic, the shape and a map.
Every file's full description and its dated decisions are in `REFERENCE.md`:
read a file's entry there before changing the file, and update it in the same PR.

## Working rules

- How we work (a low-stakes demo; keep Nikodem's effort minimal): Claude
  writes the code, pushes a `claude/...` branch, opens a PR, checks it as
  far as it can, then merges it itself. Never push to main directly, never
  commit secrets. Nikodem doesn't review code; he runs `.\run_all.ps1`
  when asked (pull + the whole pipeline), and Claude reads the output from
  `data/last_run.txt` on his laptop. Ask him only for things only he can do:
  Slack clicks, app settings, AWS deploys and logins, decisions about CS logic.
- Windows + PowerShell. Activate the env with `.venv\Scripts\Activate.ps1`,
  run scripts from the repo root (paths are relative to it). CDK runs from
  `infra/` with `--profile cairnpath`.
- Pinned dependencies live in `requirements.txt`. Add, never overwrite.
- Thresholds and time windows live in `settings.toml`, not in the scripts.
- Integrations are configuration, not code: anything tied to one workspace,
  account or environment (Slack channels and member IDs, URLs, the LLM model
  and price, AWS region and bucket) lives in its own `settings.toml` section
  ([slack], [llm], [aws], ...); secrets live only in `.env` (and, in AWS,
  Parameter Store). Moving to a new workspace or provider = edit settings and
  .env, never a script.
- Files one step hands to the next are named in settings.toml [outputs]
  (`output_file(name)`, `out_sql(name)`), never a path typed into SQL. The step
  order is one list, [pipeline], read by run_all.ps1 and the engine Lambda.
- `data/` is generated by `generate_events.py` and is git-ignored.
- Keep it lean: no new flags, tables or tools without a reason.
- A refactor must leave the outputs identical, byte for byte (sorts without ties).
- Fix review findings now, in the same change or PR. Don't defer them to
  "later": deferred fixes get lost.
- When a fix or concept has a real-world angle (something a TAM meets
  with customers, or a good interview story), add a short tip on it.
  Keep it brief and only when it's genuinely useful.

## Scope: a CSM cockpit

This is a cockpit for the CS team, not an org-wide engagement tool.
- Customer messaging triggered by usage or plan limits belongs to Product.
  Churn and expansion flags never send usage, plan-limit or upgrade
  messages: they ask the pool or CSM to investigate and analyse (the one
  email is Self-service Shelfware's adoption content, below).
- Self-service churn and expansion rows go to the Self-service report
  (routed_to = 'report') for analysis across accounts.
- Onboarding programmes (activation welcome emails, workshop invites) stay:
  they are CS one-to-many engagement, not utilisation messaging. So does
  adoption content for Self-service (e.g. the use-case inspiration email for
  Shelfware): it teaches, it never mentions plan limits or upgrades.
- Apply the same test to anything new: investigate and analyse first.

## The fake product

Cairnpath, a fictional product analytics SaaS. Customers pay for an
annual committed event volume; seats are free and unlimited; paid add-ons
(e.g. experiments) are the expansion path.

## Tiers

| Tier | CS coverage | Where flags go |
| --- | --- | --- |
| Self-service | None | Automated emails and self-onboarding |
| Scale | Pooled CS team | Shared CS queue, workshop invites |
| Enterprise | Named CSM | Straight to the CSM, plus QBR briefs |

Book of business: ~500 accounts, Europe only, in four sub-regions
(UK&I, DACH, France & Benelux, Nordics). 48 Enterprise (6 CSMs, 8 each),
150 Scale (one pooled team per region: a queue plus named members, about 1
per 15-20 accounts: UK&I 3, DACH 2, F&B 2, Nordics 1), 300 Self-service. Show counts next
to percentages in reports: small segments mislead.

CRM table (`data/crm_accounts.csv`): account_id, account_name, tier, region,
contract_start, renewal_date, contracted_events, add_ons, csm_owner
(Enterprise), cs_pool (Scale: the queue tasks go to), pool_owner (Scale:
the named pool member who owns it, optional), last_qbr_date and next_qbr_date
(Enterprise, roughly quarterly; some overdue and not rebooked), arr (optional;
missing = estimated from contracted_events x the list price in [money]),
status (churned = left at its renewal), customer_since (first signed; renewals
keep it) and csm_since (when the CSM took it), the last three optional, for the
year's history. Contract sizes vary per account (half to double the tier's middle size).
Pipeline-written facts
(e.g. "welcome sent") go in an action log, not the CRM.

CS team table (`data/cs_team.csv`): owner_id, owner_name, owner_type
(csm | pool | member), region, manager, pool (a member's pool). Scale
accounts get a named member in turn (round robin per pool, no random draws);
meetings on them are that member's, workshops stay the pool's. Tasks still go
to the pool queue; the cockpit counts a member's work as tasks routed to them
plus pool-queue tasks on their own accounts.

## Event schema

One JSON event per line, one file per day in `data/events/`.

- All events: event_id, event_name, event_type (product | system),
  timestamp (UTC), account_id
- Product events only: user_id
- Optional: properties, context
- Product events: sdk_installed, chart_created, dashboard_shared,
  cohort_created, experiment_launched, user_invited, data_export
- System events: daily_event_volume (properties.event_count),
  ingestion_error (properties.error_code)
- Derived in SQL, never emitted: first event / go-live date
- Engagement events (`data/engagement/`, view `engagement`, event_type
  engagement): email_sent, email_opened, workshop_attended, meeting_held,
  with properties.owner_id (csm_*, pool_*, automated) and properties.topic
  (getting_started, onboarding_workshop, advanced_workshop, qbr, kickoff,
  check_in, churn_call, activation_call, growth_call, follow_up; from actions.py: welcome_pack,
  invite_your_team, need_help_starting, use_case_inspiration; follow-ups
  invite_your_team_followup, need_help_starting_followup, customer_story). user_id = the customer user who
  responded or attended. context.source says who wrote it (cs_history from
  the generator, actions.py for new actions, slack for clicks, cockpit for
  managers' decisions). Slack clicks add task_claimed events and meeting_held
  with properties.outcome, .note and .slack_user. The cockpit adds
  task_assigned (properties.owner_id = new owner, topic = flag, .status,
  .manager), handback_approved and forecast_set (a renewal forecast: .status =
  renew | downsize | churn, .amount, .note = reason, .owner_id = who,
  .outcome = owner | manager; internal, never a customer touch) and
  next_step_set (action planned: .status = call | qbr | email | internal,
  .due, .note, .owner_id, .outcome; internal too).

## The four flags

1. Activation (first contracts from the last 45 days only: a renewal isn't
   onboarding, found by customer_since or events from before the term). Statuses:
   - Activated: SDK installed and 2+ active users within 14 days of
     contract start
   - Activating: under 14 days, not all signals yet (no action)
   - Stalled: 14+ days, SDK in but fewer than 2 users
   - Silent: 10+ days since contract, no events at all
   - Handoff gap: events but no CRM row (alert CS ops, no customer email)
   - No CSM assigned: Enterprise account in scope with empty csm_owner
     (alert CS ops)
   Actions route by tier: Self-service automated, Scale to the regional
   pool, Enterprise to the named CSM.
2. Churn risk (accounts live for the full 90 days). Usage signals:
   utilisation under 40% and lower each month for two months; weekly
   active users 30%+ below their 90-day average and at least one whole user
   fewer (small accounts). One = Watch, both = Act.
   Ingestion errors (5+ in 30 days, rising) only count next to a usage
   signal, and push Watch up to Act with a "technical check first" action.
   Self-service rows go to the Self-service report.
   Shelfware: live 60+ days (go-live) and 30-day utilisation never reached
   40%: flat and low, never ramped up. Status Shelfware. Scale and
   Enterprise: adoption review and a ramp plan before renewal (renewal
   within 3 months: call this week about the renewal volume). Self-service:
   automated use-case inspiration email (topic use_case_inspiration).
   Accounts already at Watch or Act keep that status.
3. Expansion (accounts live for the full 90 days). Stays with CS: the
   CSM builds the growth case, Sales only signs. Volume signal: 90%+ of
   contract already, or 80%+ and climbing 3+ points a month fast enough to
   pass 90% before renewal. Breadth signal: active users up 25%+ in two
   months. Volume + breadth = Act (action depends on timing: overage now,
   renewal within 3 months, or mid-term). Volume only = Watch with a
   tracking check (rising volume with flat users is often over-tracking).
4. QBR (Enterprise). QBR coming up: next QBR in the next 30 days, so the
   CSM prepares it; `qbr.py` builds a facts pack per account (usage,
   forecast, weekly active users trend, underused add-ons, pseudonymised
   key users, champion trend, errors, open flags). A champion is a top user
   doing 2x+ what the next one does; otherwise "no single champion". QBR overdue: live 4+ months, last
   QBR 120+ days ago or never, nothing booked in 30 days: book one.
   `brief.py` has an LLM (Claude Sonnet 5.5 via the Anthropic API) write a
   one-page brief per pack, ending with one suggested ask. Every number in
   the draft is checked against the pack; untraceable ones are listed as
   "unverified" at the bottom. Real user IDs go back in after the model.
   QBR first: with a QBR in the next 30 days, an Enterprise account's churn
   and expansion flags get no separate task. The QBR task lists them ("also
   in the brief"), they're logged "covered by the QBR", no "No meeting"
   escalation, and team_report.py counts the QBR as the action when the
   signal came in the 30 days before it. The flag rows stay, for tracking.
   If the QBR date passes with no QBR held (view qbr_slips, from the action
   log), the flag is raised again as a normal task, never handed to a QBR
   again, and a newly booked QBR no longer holds back the escalation.

## Design rules

- SQL computes every fact; the LLM only writes them up.
- Every flag shows its reasons (e.g. "utilisation 32% and falling").
- Actions are sent once only (idempotent), logged in the action log.
- Users are pseudonymised before anything reaches an LLM.
- Use the data's as-of date (max event date), never today().
- Utilisation divides by days live in the window (max 30), so new
  accounts aren't penalised and silent days still count.


## The shape

One run, in [pipeline] order (laptop: `.\run_all.ps1`; AWS: the engine Lambda):

1. **In:** `pull_clicks.py` (Slack clicks from AWS), `check_inputs.py` (stops on
   ERROR), `cockpit_sync.py` (managers' decisions, checked again), `ingest.py`
   (the events read once into a Parquet store).
2. **Facts:** `flags.py` -> `journeys.py` -> `team_report.py` -> `backtest.py`,
   `onboarding_report.py`, `history.py` (the year replayed week by week),
   `retention.py` (GRR, NRR). All SQL in DuckDB over the views in `cairnpath_db.py`.
3. **Act (laptop only):** `actions.py` posts tasks to Slack once, logs them.
4. **Show:** `export_views.py` (through `facts.py`) -> `views_data.json` ->
   `views.html` and one page per person (`roles.py`); `handover.py --dry-run`
   marks briefs out of date. In AWS: `to_parquet.py` for Athena and the public
   site.
5. **AI, on request only:** `brief.py` (QBR briefs), `handover.py` (handover
   briefs, from `documents.py`), through `llm.py` (budgets and the spend ledger).

AWS (`infra/`, CDK): a private KMS-encrypted bucket; upload -> check Lambda ->
engine Lambda (gated on the check, plus a daily schedule); Slack listener on API
Gateway; Athena over outputs/; the public demo site on CloudFront; GuardDuty,
Access Analyzer, Cost Anomaly Detection; a data perimeter in the bucket policy.

AI:

- `brief.py`: QBR briefs; `handover.py`: handover briefs with redaction and the leak check.
- `stories/`: three hand-written account stories and their answer key (tests only).

AWS (run by Nikodem, signed in with `aws login --profile cairnpath`):

- `upload.py`: inputs to the bucket, only what changed.
- `request_briefs.py`: the only way the model runs in AWS.
- `put_key.py`: secrets into Parameter Store, never printed.
- `security_check.py`: live IAM checks; `access_report.py`, `guardduty_report.py`: read-only reports.
