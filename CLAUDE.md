# Cairnpath engagement engine

A hands-on demo project: a signal-triggered customer engagement engine.
Fake product usage data goes in; flags come out that tell Customer Success
when to act and what to do. Built locally first, then moved to AWS.

The owner (Nikodem) is a Customer Success leader rebuilding hands-on
technical skills. Explain changes in plain language, keep code readable
with short comments, and prefer small steps he can review.

## Working rules

- Never commit or push unless asked. Show the change and let him commit.
- Windows + PowerShell. Activate the env with `.venv\Scripts\Activate.ps1`,
  run scripts from the repo root (paths are relative to it).
- Pinned dependencies live in `requirements.txt`. Add, never overwrite.
- Thresholds and time windows live in `settings.toml`, not in the scripts.
- `data/` is generated by `generate_events.py` and is git-ignored.
- Keep it lean: no new flags, tables or tools without a reason.
- Fix review findings now, in the same change or PR. Don't defer them to
  "later": deferred fixes get lost.
- When a fix or concept has a real-world angle (something a TAM meets
  with customers, or a good interview story), add a short tip on it.
  Keep it brief and only when it's genuinely useful.

## Scope: a CSM cockpit

This is a cockpit for the CS team, not an org-wide engagement tool.
- Customer messaging triggered by usage or plan limits belongs to Product.
  Churn and expansion flags never send usage, plan-limit or upgrade
  messages: they ask the pool or CSM to investigate and analyse (the one
  email is Self-service Shelfware's adoption content, below).
- Self-service churn and expansion rows go to the Self-service report
  (routed_to = 'report') for analysis across accounts.
- Onboarding programmes (activation welcome emails, workshop invites) stay:
  they are CS one-to-many engagement, not utilisation messaging. So does
  adoption content for Self-service (e.g. the use-case inspiration email for
  Shelfware): it teaches, it never mentions plan limits or upgrades.
- Apply the same test to anything new: investigate and analyse first.

## The fake product

Cairnpath, a fictional product analytics SaaS. Customers pay for an
annual committed event volume; seats are free and unlimited; paid add-ons
(e.g. experiments) are the expansion path.

## Tiers

| Tier | CS coverage | Where flags go |
| --- | --- | --- |
| Self-service | None | Automated emails and self-onboarding |
| Scale | Pooled CS team | Shared CS queue, workshop invites |
| Enterprise | Named CSM | Straight to the CSM, plus QBR briefs |

Book of business: ~500 accounts, Europe only, in four sub-regions
(UK&I, DACH, France & Benelux, Nordics). 48 Enterprise (6 CSMs, 8 each),
150 Scale (one pooled team per region), 300 Self-service. Show counts next
to percentages in reports: small segments mislead.

CRM table (`data/crm_accounts.csv`): account_id, account_name, tier, region,
contract_start, renewal_date, contracted_events, add_ons, csm_owner
(Enterprise), cs_pool (Scale), last_qbr_date and next_qbr_date
(Enterprise, roughly quarterly; some overdue and not rebooked). Pipeline-written facts
(e.g. "welcome sent") go in an action log, not the CRM.

CS team table (`data/cs_team.csv`): owner_id, owner_name, owner_type
(csm | pool), region, manager.

## Event schema

One JSON event per line, one file per day in `data/events/`.

- All events: event_id, event_name, event_type (product | system),
  timestamp (UTC), account_id
- Product events only: user_id
- Optional: properties, context
- Product events: sdk_installed, chart_created, dashboard_shared,
  cohort_created, experiment_launched, user_invited, data_export
- System events: daily_event_volume (properties.event_count),
  ingestion_error (properties.error_code)
- Derived in SQL, never emitted: first event / go-live date
- Engagement events (`data/engagement/`, view `engagement`, event_type
  engagement): email_sent, email_opened, workshop_attended, meeting_held,
  with properties.owner_id (csm_*, pool_*, automated) and properties.topic
  (getting_started, onboarding_workshop, advanced_workshop, qbr, kickoff,
  check_in, churn_call, activation_call, growth_call, follow_up; from actions.py: welcome_pack,
  invite_your_team, need_help_starting, use_case_inspiration). user_id = the customer user who
  responded or attended. context.source says who wrote it (cs_history from
  the generator, actions.py for new actions, slack for clicks). Slack clicks
  add task_claimed events and meeting_held with properties.outcome, .note
  and .slack_user.

## The four flags

1. Activation (contracts from the last 45 days only). Statuses:
   - Activated: SDK installed and 2+ active users within 14 days of
     contract start
   - Activating: under 14 days, not all signals yet (no action)
   - Stalled: 14+ days, SDK in but fewer than 2 users
   - Silent: 10+ days since contract, no events at all
   - Handoff gap: events but no CRM row (alert CS ops, no customer email)
   - No CSM assigned: Enterprise account in scope with empty csm_owner
     (alert CS ops)
   Actions route by tier: Self-service automated, Scale to the regional
   pool, Enterprise to the named CSM.
2. Churn risk (accounts live for the full 90 days). Usage signals:
   utilisation under 40% and lower each month for two months; weekly
   active users 30%+ below their 90-day average and at least one whole user
   fewer (small accounts). One = Watch, both = Act.
   Ingestion errors (5+ in 30 days, rising) only count next to a usage
   signal, and push Watch up to Act with a "technical check first" action.
   Self-service rows go to the Self-service report.
   Shelfware: live 60+ days (go-live) and 30-day utilisation never reached
   40%: flat and low, never ramped up. Status Shelfware. Scale and
   Enterprise: adoption review and a ramp plan before renewal (renewal
   within 3 months: call this week about the renewal volume). Self-service:
   automated use-case inspiration email (topic use_case_inspiration).
   Accounts already at Watch or Act keep that status.
3. Expansion (accounts live for the full 90 days). Stays with CS: the
   CSM builds the growth case, Sales only signs. Volume signal: 90%+ of
   contract already, or 80%+ and climbing 3+ points a month fast enough to
   pass 90% before renewal. Breadth signal: active users up 25%+ in two
   months. Volume + breadth = Act (action depends on timing: overage now,
   renewal within 3 months, or mid-term). Volume only = Watch with a
   tracking check (rising volume with flat users is often over-tracking).
4. QBR (Enterprise). QBR coming up: next QBR in the next 30 days, so the
   CSM prepares it; `qbr.py` builds a facts pack per account (usage,
   forecast, weekly active users trend, underused add-ons, pseudonymised
   key users, champion trend, errors, open flags). A champion is a top user
   doing 2x+ what the next one does; otherwise "no single champion". QBR overdue: live 4+ months, last
   QBR 120+ days ago or never, nothing booked in 30 days: book one.
   `brief.py` has an LLM (Claude Sonnet 5.5 via the Anthropic API) write a
   one-page brief per pack, ending with one suggested ask. Every number in
   the draft is checked against the pack; untraceable ones are listed as
   "unverified" at the bottom. Real user IDs go back in after the model.
   QBR first: with a QBR in the next 30 days, an Enterprise account's churn
   and expansion flags get no separate task. The QBR task lists them ("also
   in the brief"), they're logged "covered by the QBR", no "No meeting"
   escalation, and team_report.py counts the QBR as the action when the
   signal came in the 30 days before it. The flag rows stay, for tracking.
   If the QBR date passes with no QBR held (view qbr_slips, from the action
   log), the flag is raised again as a normal task, never handed to a QBR
   again, and a newly booked QBR no longer holds back the escalation.

## Design rules

- SQL computes every fact; the LLM only writes them up.
- Every flag shows its reasons (e.g. "utilisation 32% and falling").
- Actions are sent once only (idempotent), logged in the action log.
- Users are pseudonymised before anything reaches an LLM.
- Use the data's as-of date (max event date), never today().
- Utilisation divides by days live in the window (max 30), so new
  accounts aren't penalised and silent days still count.

## Files

- `DATA_CONTRACT.md`: the five inputs, their columns and meaning, which
  are required, what stops working without each, and what is still
  hard-coded. Update it whenever an input or a column changes.
- `settings.toml` + `settings.py`: every threshold and time window in one
  place (activation, churn, expansion, QBR, journeys, team report, email
  hour). Scripts read `SETTINGS[...]`; never hard-code a number in a script.
  Tiers, routing and the utilisation definition are still in the SQL (next:
  move them into settings; see DATA_CONTRACT.md).
- `generate_events.py`: ~500 fake accounts with personalities (healthy,
  declining, power_user, new_customer, shelfware, stalled, never_onboarded,
  handoff_gap) mixed by weight (new customers sign all through the window
  and ramp their volume up over the first month; shelfware is flat at about
  a quarter of the contract;
  stalled and silent ones are recent), 90 days of events, the CRM table and the
  CS team table. About 4 in 10 accounts have a champion (one user far more
  active than the rest). Product use follows a working week (quiet
  weekends); event volume doesn't (the customer's end users never stop).
  Seeded, so output is repeatable.
  Also writes the CS history to `data/engagement/` (own random generator):
  getting-started emails and opens, fortnightly Scale workshops, QBRs on
  the CRM dates, kickoffs, check-ins, churn and growth calls and follow-ups, each owner with their
  own speed, reacting to the day each account's problem shows in its
  numbers. 1 in 5 new Self-service/Scale accounts is a control group (no
  email; planted effect: SDK in after 5 days, not 2). Working hours, local
  time, no weekend meetings.
  Also writes `data/onboarding_holdout.csv`: the control group as a
  real-world fact (the programme's own list), which every sender checks.
  Also writes `data/answer_key.csv` (each account's personality and
  welcome group): for testing only, the flags must never read it.
- `cairnpath_db.py`: shared DuckDB setup. `connect()` returns a connection
  with the views events (schema declared explicitly), engagement (the CS
  history, same schema), crm, cs_team, as_of
  and utilisation, monthly_usage (utilisation and users per 30-day month),
  qbr_schedule (QBR coming up / overdue), qbr_slips (flags handed to a
  QBR that didn't happen, from the action log), daily_util_30d (30-day
  utilisation on every day, rounded like the flags), last_touch (last CS touch,
  last meeting, getting-started email opened or not, per account).
  Every script uses it; define views here, once.
- `explore.py`: DuckDB summaries by tier, region and CSM, plus CS
  engagement week by week and meetings by owner.
- `flags.py`: the activation, churn and expansion flags. One row per
  flagged account, with reasons, routed_to and action; saved to
  `data/flags_activation.csv`, `data/flags_churn.csv` and
  `data/flags_expansion.csv`; the QBR flag to `data/flags_qbr.csv`.
- `check_flags.py`: tests the flags against the answer key (run `flags.py`
  first): share of each personality found, false alarms, and every miss by
  name. Re-run it after any change to a flag rule.
- `journeys.py`: rules on the last touch (run `flags.py` first). "Email
  never opened": Self-service stalled/silent, getting-started email 5+ days
  old and unopened -> CS ops checks the contact. "No meeting in 30 days":
  churn or expansion Act (Scale/Enterprise) for 14+ days with no meeting
  in 30 days, and no QBR booked in the next 30 days ->
  escalated to the owner's manager (one Slack message per manager). Saved
  to `data/flags_journey.csv`, same columns as the flags.
- `team_report.py`: time to action by owner and manager (run `flags.py`
  and `journeys.py` first). Signal date = first day the account's 30-day
  utilisation crossed the flag's line (rebuilt from usage); call date =
  first churn, growth or activation call (check-ins don't count; a QBR
  counts when the signal came in the 30 days before it, column via);
  a call up to 14 days before the signal counts as 0 days ("called
  early"). Also escalations and meetings in 90 days. Action status (view
  action_status, from the action log): each task Open, Claimed (Slack),
  Done (the right meeting since it was sent: churn -> churn call or QBR,
  expansion -> growth call or QBR, QBR -> the QBR, activation and
  escalations -> any meeting; a check-in never closes a churn task) or
  Resolved (the flag went away; the only way CS ops tasks close), with its
  age. Managers see unclaimed pool tasks and CS ops items, oldest first.
  Outcome not measured yet.
- `onboarding_report.py`: welcomed vs. control (run `generate_events.py`
  first). New Self-service/Scale accounts that got the getting-started email
  vs. the onboarding holdout: SDK installed, median days to SDK and to first
  chart (speed), activated in 14 days for accounts 14+ days old (outcome),
  overall and by tier, counts next to percentages. Planted effect: shows the
  method, doesn't prove emails work.
- `export_views.py`: everything the views need, to `data/views_data.json`
  (run `generate_events.py`, `flags.py` and `journeys.py` first). Reuses the
  reports' SQL through `team_report.add_views(con)` and
  `onboarding_report.add_views(con)`, so the page and the reports agree.
  Counts only, never real user IDs. Also builds `data/views.html` from
  `views_template.html` (the data goes into its `__VIEWS_DATA__` slot): four
  tabs (account timeline, onboarding, CS team, book of business), opens in any
  browser offline. The page only draws; the numbers come from the export.
- `actions.py`: turns flag rows into actions, once only (run `flags.py`
  first). Checks `data/action_log.csv` by account, flag and status, then
  logs each new action. Queue tasks for CSMs, pools and CS ops post to
  Slack #cs-queue, one message per owner; customer emails stay simulated
  and are previewed in #email-preview. Webhooks in `.env`
  (SLACK_WEBHOOK_QUEUE, SLACK_WEBHOOK_EMAIL): secrets, like the API key.
  An action is logged only after its post worked, so failures retry.
  Holdout accounts get no onboarding emails (logged as "held out", never
  sent) and their queue tasks carry a note not to send one by hand.
  Each customer email is also written as an email_sent event to
  `data/engagement/<run date>.jsonl`. `generate_events.py` clears the log,
  since new data makes old actions meaningless.
  Reads the journey rows too, and shows each account's last CS touch under
  every Slack task. Owners in settings.toml [slack] interactive_owners get one
  card per task with buttons (via the bot token, one a second) instead of
  the digest. QBR first: churn/expansion rows of an account with a QBR in
  the next 30 days are logged "covered by the QBR" and named on its QBR task.
  `none` and `report` rows aren't actions. The log only grows; delete it
  to start over.
- `slack_loop.py`: shared Slack pieces (task cards, .env tokens, appending
  click events). `listener.py`: Socket Mode listener (`python listener.py`,
  leave it running): "I'll take it" -> task_claimed, "Log call" -> a form ->
  meeting_held with the flag's call topic, "Open timeline" -> the cockpit
  page at `#acc_xxx`. Clicks are dated on the run date. Which owners get
  cards (and which get DMs) is in settings.toml [slack]; everyone else keeps
  the digest. Tokens in .env: SLACK_BOT_TOKEN (xoxb), SLACK_APP_TOKEN (xapp),
  SLACK_DEMO_USER.
- `qbr.py`: QBR facts packs (run `flags.py` first). Writes
  `data/qbr_facts.json` (pseudonymised) and `data/qbr_user_key.csv` (the
  real user IDs; never sent to an LLM).
- `brief.py`: QBR briefs from the facts packs (run `qbr.py` first; needs
  `ANTHROPIC_API_KEY` in the git-ignored `.env`). Writes
  `data/briefs/<account_id>.md`. `python brief.py acc_037` for one account.
  The API key lives only in `.env`: never print it, log it or commit it.
